# 業務フローフォーマット JSON 作成ルール

## 1. 目的

本ルールは、業務フローチャートを描画するための `flow_model.json` を、特定業務に依存しすぎず汎用的に作成するための指針を定めるものである。  
このJSONは描画データではなく、**業務プロセスの意味モデル** を表現することを目的とする。

本ルールに従って作成されたJSONは、以下のような用途を想定する。

- React Flow + ELK による自動レイアウト表示
- AIエージェントによる業務文書からの構造抽出結果の保存
- 業務レビュー、監査レビュー、改善検討のための可視化
- 将来的な複数ビュー生成や複数ページ分割の基礎データ

---

## 2. 基本方針

### 2.1 JSONは意味モデルであり、描画モデルではない
JSONには、業務上の意味と関係のみを保持する。  
以下のような描画専用情報は含めない。

- x座標 / y座標
- ノード幅 / 高さ
- エッジの折れ点
- フォントサイズ
- 色の詳細
- 絶対配置位置

### 2.2 ノードとエッジで業務構造を表現する
業務フローは、以下の考え方で表現する。

- **nodes**: 処理、判断、開始、終了などの業務上の単位
- **edges**: ノード間の遷移関係

### 2.3 判断点と分岐結果を分ける
条件分岐は以下のように表現する。

- 判断点: `type: "decision"` のノード
- 分岐結果: 当該ノードから出る複数のエッジ
- 分岐条件: `edge.condition`

つまり、条件はノードではなくエッジ側に持たせる。

### 2.4 JSONは業務上の正本とする
描画結果や画像は派生物であり、正本はJSONとする。  
後続の表示、編集、差分比較、再描画はこのJSONを基準に行う。

---

## 3. ルート構造

JSON全体は以下の構造を基本とする。

```json
{
  "schema_version": "1.0",
  "flow_id": "string",
  "title": "string",
  "description": "string",
  "lanes": [],
  "phases": [],
  "nodes": [],
  "edges": [],
  "sources": []
}
```

### 3.1 必須項目
- `schema_version`
- `flow_id`
- `title`
- `lanes`
- `phases`
- `nodes`
- `edges`

### 3.2 任意項目
- `description`
- `sources`

---

## 4. lanes の作成ルール

### 4.1 役割
`lanes` は、各ノードがどの主体に属するかを表す。  
主に以下を表現する。

- 部門
- 役職 / 承認者
- システム
- 外部取引先

### 4.2 記述単位
1レーンは、フロー図上で1本の責任主体または処理主体に対応させる。

#### 例
- 申請部門
- 承認者
- 購買部
- 経理部
- 購買システム
- 取引先

### 4.3 推奨項目
```json
{
  "id": "L001",
  "name": "申請部門",
  "type": "department"
}
```

### 4.4 type の例
- `department`
- `role`
- `system`
- `external_party`

### 4.5 作成ルール
- 同一主体は1つのレーンに統一する
- レーン名は業務利用者に分かる名称にする
- レーンを細かく分けすぎない
- 実務上の責任主体が違う場合のみ分ける

### 4.6 粒度の目安
#### 良い例
- 経理部
- 購買部
- 承認者
- 購買システム

#### 過剰に細かい例
- 経理部Aさん
- 経理部Bさん
- 購買部主任
- 購買部課長補佐

人物単位ではなく、基本は役割または組織単位で表す。

---

## 5. phases の作成ルール

### 5.1 役割
`phases` は、業務全体を意味的に区切る単位を表す。  
長いフローや複雑なフローでは必須と考える。

### 5.2 記述単位
フェーズは、業務の主要な段階ごとに分ける。

#### 例
- 申請準備
- 申請・承認
- 購買審査
- 発注
- 受入・検収
- 請求書照合
- 支払
- 事後確認

### 5.3 推奨項目
```json
{
  "id": "PH001",
  "name": "申請"
}
```

### 5.4 作成ルール
- 業務全体が時系列で追いやすいように区切る
- フェーズは過度に細分化しない
- 1フェーズに最低1ノード以上を持たせる
- レーンと違い、フェーズは時間的・業務的なまとまりで分ける

### 5.5 粒度の目安
#### 良い例
- 承認
- 発注
- 支払

#### 細かすぎる例
- 承認依頼メール送信
- 承認依頼確認
- 承認ボタン押下

後者は通常、フェーズではなくノードで表す。

---

## 6. nodes の作成ルール

### 6.1 役割
`nodes` は、業務上の処理や判断の最小単位を表す。

### 6.2 ノード種別
初期実装では以下を基本とする。

- `start`
- `end`
- `process`
- `decision`
- `document`
- `system_process`

### 6.3 推奨構造
```json
{
  "id": "N001",
  "type": "process",
  "label": "購買申請を起票する",
  "lane_id": "L001",
  "phase_id": "PH001",
  "description": "購買システム上で申請を登録する",
  "source_refs": ["SRC001"]
}
```

### 6.4 必須項目
- `id`
- `type`
- `label`
- `lane_id`
- `phase_id`

### 6.5 任意項目
- `description`
- `source_refs`

### 6.6 ノード化の判断基準
以下のいずれかに当てはまる場合、原則として1ノードにする。

- 業務上の明確な処理がある
- 誰かが実行するアクションである
- システムが実行する処理である
- 判断点である
- 文書が生成・受領される重要な場面である
- 例外や差戻しの起点になる

### 6.7 ノード化しすぎないための基準
以下のような細かすぎる操作は、単独ノードにしないことを基本とする。

- 画面を開く
- ボタンを押す
- スクロールする
- シートを切り替える

これらは業務フローではなく操作手順の粒度である。

### 6.8 label の書き方
- 業務利用者が読んで意味が分かる文言にする
- 可能な限り動詞を含める
- 短く保つ
- 長文は `description` に入れる

#### 良い例
- 購買申請を起票する
- 承認権限を確認する
- 発注書を送付する
- 三点照合を行う

#### 悪い例
- 起票
- 確認
- 実施
- 処理

曖昧すぎるラベルは避ける。

### 6.9 type の使い分け
#### `start`
フローの開始点。最低1つ置く。

#### `end`
フローの終了点。最低1つ置くことを推奨する。

#### `process`
人が行う通常処理。

#### `decision`
条件判定や承認可否などの判断点。

#### `document`
文書の生成・受領・確認を強調したい場合。

#### `system_process`
システムが自動的に行う処理。

### 6.10 decision ノードの書き方
`decision` は「何を判断するか」を表す。

#### 良い例
- 予算確保済みか
- 承認権限内か
- 見積取得が必要か
- 照合差異があるか

#### 悪い例
- Yes
- No
- 承認
- 差戻し

Yes/No はノードではなく、エッジ側で表現する。

---

## 7. edges の作成ルール

### 7.1 役割
`edges` は、ノード間の遷移関係を表す。

### 7.2 推奨構造
```json
{
  "id": "E001",
  "from": "N001",
  "to": "N002",
  "label": "承認",
  "edge_type": "normal",
  "condition": {
    "type": "text",
    "text": "承認条件を満たす"
  },
  "source_refs": ["SRC002"]
}
```

### 7.3 必須項目
- `id`
- `from`
- `to`

### 7.4 任意項目
- `label`
- `edge_type`
- `condition`
- `source_refs`

### 7.5 edge_type の例
- `normal`
- `rollback`
- `exception`
- `escalation`

### 7.6 edge の使い分け
#### `normal`
通常の順方向遷移。

#### `rollback`
差戻しや再実施など、前工程へ戻る遷移。

#### `exception`
例外処理ルート。

#### `escalation`
上位承認や別責任者へのエスカレーション。

### 7.7 edges 作成ルール
- 1つの遷移は1つのedgeで表す
- `from` と `to` は必ず既存ノードを参照する
- 条件分岐がある場合、decisionノードから複数のedgeを出す
- 差戻しは `rollback` を使って明示する
- 例外ルートは `exception` で区別することを推奨する

---

## 8. 条件分岐の表現ルール

### 8.1 基本原則
条件分岐は **decisionノード + 条件付きedges** で表現する。

#### 例
- ノード: `承認権限内か`
- エッジ1: `権限内`
- エッジ2: `権限外`

### 8.2 condition の基本形
初期実装では `type: "text"` を基本とする。

```json
{
  "type": "text",
  "text": "承認条件を満たす"
}
```

### 8.3 edge.label と condition.text の使い分け
#### `label`
図上に短く表示する文字列

#### `condition.text`
詳細条件の説明

#### 例
```json
{
  "label": "権限外",
  "condition": {
    "type": "text",
    "text": "申請金額が承認者の承認権限を超える"
  }
}
```

### 8.4 分岐の書き方パターン
#### Yes / No型
```json
{
  "label": "Yes",
  "condition": {
    "type": "text",
    "text": "条件を満たす"
  }
}
```

```json
{
  "label": "No",
  "condition": {
    "type": "text",
    "text": "条件を満たさない"
  }
}
```

#### しきい値型
```json
{
  "label": "100万円以上",
  "condition": {
    "type": "text",
    "text": "購買金額が100万円以上"
  }
}
```

#### 例外型
```json
{
  "label": "例外購買",
  "edge_type": "exception",
  "condition": {
    "type": "text",
    "text": "緊急購買または単独見積に該当する"
  }
}
```

### 8.5 decision ノードから出るedgeのルール
- 原則2本以上出ること
- それぞれ `label` を持たせることを推奨する
- 条件が分かるように `condition.text` を持たせる
- ラベル重複は避ける

---

## 9. sources の作成ルール

### 9.1 役割
`sources` は、ノードやエッジの根拠資料を表す。

### 9.2 推奨構造
```json
{
  "id": "SRC001",
  "file_name": "購買規程.pdf",
  "page": 5,
  "section": "購買申請"
}
```

### 9.3 推奨項目
- `id`
- `file_name`
- `page`
- `section`
- `quote`

### 9.4 作成ルール
- 根拠資料はできるだけ明示する
- ノードまたはエッジに `source_refs` で紐づける
- 抽象的な出典ではなく、できるだけ具体的なファイル名と節を入れる
- AI推定で根拠が薄い場合でも、空欄ではなく推定元候補を入れる方がよい

### 9.5 source_refs の付け方
#### ノードに付ける場合
その処理自体の根拠資料を表す。

#### エッジに付ける場合
その分岐条件や遷移関係の根拠資料を表す。

---

## 10. ID採番ルール

### 10.1 推奨プレフィックス
- lanes: `L001`, `L002`
- phases: `PH001`, `PH002`
- nodes: `N001`, `N002`
- edges: `E001`, `E002`
- sources: `SRC001`, `SRC002`

### 10.2 ルール
- 同一配列内で重複しないこと
- 一意であること
- 人が追いやすい規則にすること
- 桁数は固定を推奨する

---

## 11. 粒度設計ルール

### 11.1 基本
1ノード = 1業務処理 または 1判断点 を基本とする。

### 11.2 粗すぎる場合
以下のようなラベルは粗すぎる可能性が高い。

- 購買を実施する
- 支払を処理する
- 承認する

必要なら以下に分解する。

- 購買申請を起票する
- 承認権限を確認する
- 部門承認を行う
- 発注書を発行する
- 請求書を照合する
- 支払を実行する

### 11.3 細かすぎる場合
以下は細かすぎる可能性が高い。

- システム画面を開く
- 申請ボタンを押下する
- 添付ファイル欄を開く

この粒度は通常、業務フローではなく操作手順である。

### 11.4 推奨粒度
- 業務担当者や監査人がレビュー可能な粒度
- リスク・統制・差戻し・例外が識別できる粒度
- レーンやフェーズとの対応が分かる粒度

---

## 12. 長く複雑なフローを作るときのルール

### 12.1 必ず phases を使う
長い業務フローでは、フェーズなしだと見通しが悪くなる。  
そのため、複雑フローでは `phases` を必須とすることを推奨する。

### 12.2 rollback / exception / escalation を明示する
通常ルート以外は `edge_type` で区別する。

### 12.3 システム処理は明示する
人の作業とシステムの自動処理が混在する場合、`system_process` と `system` レーンを使い分ける。

### 12.4 外部主体もレーン化する
取引先、委託先、顧客などが重要なら `external_party` レーンとして表現する。

### 12.5 再申請・再実行を隠さない
差戻しや再処理は省略せず表現する。  
複雑さを恐れて省略すると、実態から乖離しやすい。

---

## 13. 汎用的に作るための判断基準

JSONを特定業務に依存させすぎないため、以下を意識する。

### 13.1 業務固有語を使いすぎない
やむを得ず固有名詞を使う場合も、一般化できるラベルを優先する。

#### 例
- 良い: 支払承認を取得する
- 固有すぎる: Z会計システムのXX承認ボタンを押す

### 13.2 ルールそのものではなく構造を表す
JSONは「どう描くか」ではなく「どう流れるか」を表す。

### 13.3 将来拡張を邪魔しない
後で以下を追加しやすいようにする。

- risks
- controls
- evidences
- subprocesses
- pages
- confidence
- review_status

## 14. 作成手順の推奨フロー

JSONを手作業またはAIで作る際は、以下の順序を推奨する。

### Step 1: フロー全体の目的を定義する
- 何の業務か
- どこからどこまでか
- 何を可視化したいか

### Step 2: 主体を洗い出す
- 部門
- 承認者
- システム
- 外部先

これを `lanes` にする。

### Step 3: 主要フェーズを定義する
- 申請
- 承認
- 発注
- 支払
など

これを `phases` にする。

### Step 4: ノードを抽出する
- 開始
- 通常処理
- 判断点
- 終了

### Step 5: エッジを張る
- 通常の順序
- 分岐
- 差戻し
- 例外
- エスカレーション

### Step 6: 条件を付ける
- decisionノードからの各edgeに `label` と `condition` を付ける

### Step 7: ソースを紐づける
- ノードまたはエッジに `source_refs` を付与する

### Step 8: バリデーションする
- 参照整合性
- ID重複
- 分岐ラベルの妥当性
- 孤立ノードの有無

---

## 15. バリデーション観点

JSON作成後は、少なくとも以下を確認する。

### 15.1 必須項目
- `flow_id`
- `title`
- `lanes`
- `phases`
- `nodes`
- `edges`

### 15.2 参照整合性
- 全 `lane_id` が存在する
- 全 `phase_id` が存在する
- 全 `from` / `to` ノードが存在する
- 全 `source_refs` が存在する

### 15.3 構造妥当性
- `start` ノードが存在する
- `end` ノードが存在することを推奨
- `decision` ノードから2本以上のedgeが出ている
- 孤立ノードがない

### 15.4 表示品質
- `label` が短く明確
- `decision` からの分岐ラベルが分かりやすい
- 差戻しや例外が `edge_type` で表現されている

## 17. まとめ

本JSON作成ルールの中核は以下である。

- JSONは描画仕様ではなく意味モデルである
- `lanes` は主体、`phases` は段階、`nodes` は処理、`edges` は遷移を表す
- 条件分岐は `decision` ノードと `edge.condition` で表現する
- 座標や描画情報は含めない
- 長いフローではフェーズ、差戻し、例外、システム主体を明示する
- 根拠資料は `sources` と `source_refs` で保持する
- 特定業務に閉じすぎず、一般的な業務構造として表現する
