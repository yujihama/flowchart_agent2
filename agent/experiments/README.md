# 比較実験: 単純なLLM実行 vs エージェント(検証+自律修正ループ)

「単純なLLM実行(1回呼び出し)で flow_model.json を安定して生成できるか」を、
エージェント(検証ツール+自律修正ループ)と比較した実験。

実行: [compare_baseline.py](compare_baseline.py)(要 `OPENAI_API_KEY`)

## 条件(公平性の担保)

両条件の差分は**検証ツールと自律修正ループの有無のみ**。

| | ベースライン(単純実行) | エージェント |
|---|---|---|
| 入力ドキュメント | 4文書全文(同一) | 4文書全文(同一) |
| スキーマ知識・設計ルール | システムプロンプトで全て提供 | 同左 |
| 検証ツール | なし | あり(UIと同一ルール) |
| 修正機会 | なし(1回のみ) | エラー0件まで自律修正 |
| 出力抽出 | コードフェンス等を寛容に除去(有利条件) | 保存ツール経由 |

課題: Order-to-Cash業務ドキュメント4点(相互参照あり、生成規模 約70-90ノード)。
判定: アプリの検証器でエラー0件(=描画可能)か。警告数は品質指標。

## 結果(2026-07-11実施)

| 条件 | モデル | 描画可能 | 警告数 | 備考 |
|---|---|---|---|---|
| ベースライン | gpt-5.6-terra | **3/3** | 0 / 0 / 0 | 最上位モデルは単発でも安定 |
| エージェント | gpt-5.6-terra | 1/1 | 0 | 検証1回でOK |
| ベースライン | gpt-4.1-mini | **2/3** | 20 / 5 / 14 | 1回は検証エラーで**描画不可** |
| エージェント | gpt-4.1-mini | **1/1** | **1** | 検証NG→自律修正→OK |

ベースライン gpt-4.1-mini の失敗例(3回目):
```
edges[29].edge_type: 未知の edge_type です: end
edges[68].edge_type: 未知の edge_type です: decision
```
スキーマに無い `edge_type` 値を捏造しており、アプリはこのJSONを受理しない。

## 考察

1. **単純実行の成功は確率的で、保証がない。** 最上位モデル(gpt-5.6-terra)は
   単発でも安定して合格したが、これは「たまたま全試行が成功した」以上の保証を
   持たない。中位モデル(gpt-4.1-mini)では3回に1回が描画不可となり、
   成功した場合も5〜20件の警告(分岐ラベル欠落等)が残った。
2. **エージェントは構造的に品質を保証する。** 保存ツールが検証にゲートされている
   ため、出力されるJSONは常にエラー0件。gpt-4.1-mini でも検証NG→自律修正→OK と
   ループが機能し、警告も1件まで解消した(ベースライン平均13件)。
3. **実運用上の含意**: 単純実行では失敗時にそれを検知する仕組みが呼び出し側に
   別途必要になる(気づかず壊れたJSONを下流に流すリスク)。エージェント方式は
   検知・修正・保証を生成プロセス自体に内包する。また、モデルを安価なものに
   差し替えても品質水準が維持される。

# 実験2: 拡充版ドキュメント(6文書・776行・約52KB)での再実験

実在の規程らしいノイズ(総則・用語定義・決裁権限別表・改訂履歴)を含む
6文書に拡充し、部分更新(パッチ)方式のエージェントで再実施(2026-07-11)。

## 結果

| 条件 | モデル | 描画可能 | 備考 |
|---|---|---|---|
| ベースライン | gpt-5.6-terra | **3/3** | 警告 1/0/0。生成規模 86〜113ノード |
| エージェント | gpt-5.6-terra | 1/1 | 初回NG→**パッチ1件**の部分更新で合格(94ノード) |
| ベースライン | gpt-4.1-mini | **1/3** | 失敗1: `edge_type: end` の捏造(エラー2件)。失敗2: **タイムアウト**(単発で巨大JSONを生成する方式自体の運用リスク)。成功時も警告4件 |
| エージェント | gpt-4.1-mini | 1/1(※) | 検証OK→パッチ2件→合格・警告1件(明示保存) |

※ 設計反復あり: 当初の「パッチのみ(全文再提出禁止)」ではminiが14回NGのまま
収束しなかった。「原則パッチ+2回連続でエラーが減らない場合のみ全文再提出可」の
ハイブイッド化、エラー件数の増減フィードバック、保存忘れ時の自動保存を追加した
改修後の再試行で合格。

## 追加の知見

1. **部分更新方式の効果**: 強いモデルではドラフト1回+パッチ1〜2件で収束し、
   全文再生成に比べトークン消費と修正時のデグレードリスクを大幅に削減できる。
2. **弱いモデルの限界はカバレッジに現れる**: gpt-4.1-mini は検証合格まで到達する
   ものの、生成規模は22ノード(terraの約1/4)にとどまった。検証は構造的な
   整合性を保証するが、**網羅性(ドキュメント内容の拾い漏れ)までは保証しない**。
   網羅性の担保には要素数の下限チェックやカバレッジ検証の追加が今後の課題。
3. **フェイルセーフの違い**: ベースラインの失敗は「壊れたJSONがそのまま出力される」
   (フェイルオープン)だが、エージェントの失敗は「保存されない」(フェイルクローズ)。
   下流工程を壊さないという意味で、失敗の質が異なる。
